Auth and session sequences

How sign in, sessions, email tokens, Google and account deletion work step by step. Each sequence reads from top to bottom, and each arrow is one call.

Tokens and lifetimes

TokenForm and storageLifetime and use
Access tokenJWT in the leafy_at cookie. Never readable by page scripts.15 minutes (900 s). Next.js refreshes it when it is missing or within 30 s of expiry.
Refresh tokenOpaque random value in leafy_rt. The database keeps only its hash, with a family_id.30 days, and the whole family ends after 90 days. It rotates on every use.
Verify email tokenRandom 256 bit value, stored as sha256 in auth_token.24 hours. One use, consumed by a single atomic UPDATE.
Reset password tokenThe same shape as the verify token, type reset_password.1 hour. One use. A reset revokes every refresh family.
OAuth cookieState, nonce and the PKCE verifier. httpOnly, SameSite=Lax, __Host- prefix.10 minutes. Single use, cleared after the callback.
Google ID tokenChecked on the server with cached JWKS. Never stored.Used once to find or create the user.

Rules the sequences follow

Uniform

No hints for attackers

Wrong credentials, an unknown email and a user without a password all give the same 401. Forgot password always answers 200. Bad email tokens give one 400.

Rotation

Reuse revokes the family

A rotated token used again inside 10 s is a harmless concurrent refresh. After 10 s it counts as theft and the whole family is revoked.

Secrets

Only the API holds them

Next.js and the browser never see GOOGLE_CLIENT_SECRET. Email tokens are stored hashed, and no token or code stays in a URL after the callback.

Outbox

Delete works without S3

Image keys are queued in storage_deletion in the same transaction that deletes the user. A drain job removes the files later.
