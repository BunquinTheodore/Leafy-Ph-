Auth and session sequences

How sign in, sessions, Google, setting a password and account deletion work step by step. Each sequence reads from top to bottom, and each arrow is one call.

Tokens and lifetimes

TokenForm and storageLifetime and use
Access tokenJWT in the leafy_at cookie. Never readable by page scripts.15 minutes (900 s). Next.js refreshes it when it is missing or within 30 s of expiry.
Refresh tokenOpaque random value in leafy_rt. The database keeps only its hash, with a family_id.30 days, and the whole family ends after 90 days. It rotates on every use.
Firebase ID tokenPosted once by the browser. Checked in FastAPI against cached Google certificates. Never stored.About 1 hour. Used once to find or create the user. Its sign in time marks the session as a recent Google session for 10 minutes.

Rules the sequences follow

Uniform

No hints for attackers

Wrong credentials, an unknown email and a user without a password all give the same 401. Leafy sends no email, so there is nothing to enumerate.

Rotation

Reuse revokes the family

A rotated token used again inside 10 s is a harmless concurrent refresh. After 10 s it counts as theft and the whole family is revoked.

Secrets

Only the API holds them

There is no Google client secret at all: the API only verifies a signature. Refresh tokens are stored hashed, and no token ever sits in a URL.

Outbox

Delete works without S3

Image keys are queued in storage_deletion in the same transaction that deletes the user. A drain job removes the files later.
